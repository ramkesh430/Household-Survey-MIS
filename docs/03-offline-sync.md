# Offline data collection & synchronisation (Phase 2)

## Who works offline
| Role | Mode |
|---|---|
| Enumerator | **Local-first.** Households and own surveys live on the device and sync in the background. |
| Admin | Local-first for households and surveys they collect. The "सर्भरका सबै" tab is an online list of everyone's surveys. |
| Supervisor | Online (read-only view of the ward). Review and approval come in Phase 3. |

## Pieces
| Piece | File | Purpose |
|---|---|---|
| Service worker | generated by `vite-plugin-pwa` | Precaches the app shell, JS/CSS and Nepali fonts (≈ 715 KB). The app opens with **no network**. API responses are *not* cached by the service worker. |
| Device database | `client/src/offline/db.js` | IndexedDB, **one database per user** (`hhs-offline-u<id>`). Stores: `wards`, `settlements`, `households`, `surveys`, `outbox`, `meta`. |
| Local operations | `client/src/offline/store.js` | Register a household, start/save/submit a survey, record GPS, resolve conflicts. Every write updates IndexedDB and queues an operation in the **outbox**, in one transaction. |
| Sync engine | `client/src/offline/sync.js` | Pushes the outbox in order, then pulls changes (`GET /api/sync/pull?since=`). |
| UI | `SyncBar`, `/sync` (SyncCenter), `SurveyEditor` | Online/offline state, pending count, last sync, conflicts and errors, "अहिले सिंक". |

## When sync runs
- At app start.
- On the browser's `online` event.
- Every 60 s while the app is open.
- When the tab becomes visible again.
- 1.5 s after any local change.
- On the "अहिले सिंक" button.

Network errors retry with backoff: 5 s → 15 s → 1 min → 5 min → 15 min. Reconnecting or pressing the button forces an immediate retry.

## Correctness guarantees
1. **Atomic local writes.** Data and its outbox operation are written in one IndexedDB transaction, so a crash cannot leave one without the other.
2. **Ordered, dependency-aware push.** Operations go strictly in queue order. If a household's operation fails, that household's survey waits; other households continue.
3. **Idempotent requests.** Households and surveys carry device-generated UUIDs. Every save or submit carries an `op_id` that the server stores in `surveys.last_op_id`. If a response is lost and the request is retried, the server acknowledges it instead of applying it twice or reporting a false conflict.
4. **No silent overwrites.** Saves send the server `version` the edits were based on. If the server copy changed meanwhile (another device or a supervisor), the survey is marked **conflict** and both copies are kept. The sync centre lists the questions that differ and offers *मेरो संस्करण राख्नुहोस्* or *सर्भरको संस्करण राख्नुहोस्*.
5. **Coalescing.** At most one pending save per survey. It always sends the latest answers, so 200 keystrokes offline become one request.
6. **Server stays authoritative.** Every save is re-validated and re-computed on the server. A submission the server rejects (422) is reopened as a draft on the device, with the server's error list shown on the form.
7. **Edits during sync are kept.** If answers change while a save is in flight, the newer local answers are kept and another save is queued.
8. **Duplicate households from two devices.** The server's unique `(settlement, house_no, family_no)` returns 409 with the existing household. The enumerator chooses **जोड्नुहोस्** (link my survey to that household), **नम्बर सच्याउनुहोस्** (renumber and retry) or **मेटाउनुहोस्** (discard).
9. **Clock-safe incremental pull.** The server returns its own `serverTime` and the client sends it back as `since`. The DB session runs in UTC, and a 2 s overlap covers second-precision timestamps.
10. **Data retention.**
    - The app asks the browser for persistent storage (`navigator.storage.persist()`).
    - Logging out keeps unsent work on the device, with a warning; it is sent after the same user logs in again.
    - A session ends only on a definitive 401. Network or server trouble never logs the user out.

## Sessions while offline
The access token lasts 15 minutes and the refresh token 30 days. Offline, the app keeps working from the device database; nothing needs a token until sync. Back online, the engine refreshes the token. If the refresh token has expired (more than 30 days offline), the user logs in again and the queued work is then sent.

## GPS
"📍 घरको GPS स्थान लिनुहोस्" asks for location only when pressed, which triggers the browser's own permission prompt.
- High accuracy, 30 s timeout. Accuracy is shown (amber above ±50 m).
- Coordinates outside Nepal are refused on the device and again on the server (lat 26–31, lng 80–89).
- Submitting without GPS asks for confirmation.
- The point is stored in `surveys.gps_lat/gps_lng/gps_accuracy_m/gps_captured_at`.

## Bikram Sambat date
`BsDatePicker` shows a BS month calendar (बैशाख … चैत, आइत … शनि) with an "आज" button. Future dates are disabled, and typed dates (Nepali or Latin digits) are checked against the real calendar. Conversion uses `nepali-date-converter`, verified in tests against the New Year dates of 2080–2083 BS.

## Limits / notes
- Browsers on iOS may clear site data after long inactivity even with persistence requested. Enumerators should sync daily (the bar shows "अन्तिम सिंक").
- Background Sync (syncing while the app is closed) is not used. Browser support is limited and the queue needs the user's session. Sync runs whenever the app is open.
- An admin's first pull downloads all households (capped at 20,000 per pull).

Covers offline entry, ordered upload, lost-response retry, conflict detection and resolution, pull refresh, server-rejected submit, offline submit with GPS, the duplicate-household link and renumber flows, and per-user isolation.
- `server/test/sync.test.js`: pull scoping, incremental pull, uuid-based create, idempotent save and submit, GPS range.
- Browser check (Chrome, production build): log in → go offline → reload (served by the service worker) → register household → fill survey → GPS → BS date → 3 operations pending, nothing on the server → reconnect → automatic sync → verified rows in MySQL.
